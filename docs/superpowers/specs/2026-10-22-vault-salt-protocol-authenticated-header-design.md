# Vault Salt, Protocol 1/2, and Authenticated Metadata Design

## Goal

Close the Password Manager gaps against the paper by persisting a distinct
per-website authentication salt, invoking the existing Auth Protocol 1 flow
when a credential is added, invoking Protocol 2 before a credential is
revealed, and authenticating the vault file metadata together with its AES-GCM
ciphertext.

## Scope and constraints

- Change only the per-site salt, Password Manager Protocol 1/2 integration,
  and vault authenticated-metadata/migration behavior described here.
- Do not change QR Sync, the Auth protocol's cryptographic construction, the
  password-generation behavior, the existing master-password Argon2id
  parameters, or the established Password Manager UI flow.
- Passwords remain user-entered. The feature does not add a password
  generator.
- Auth accounts and website Protocol 1/2 server records are in-process demo
  data. They reset when the application exits. The demo is not a real website
  server or a production website-authentication integration.
- Keep the plaintext website index so websites remain listable/searchable while
  the vault is locked.

## Current behavior and gaps

- `VaultEntry` already has a `salt` field and the encrypted-entry serializer
  preserves it, but Password Manager currently leaves it empty for new entries.
- `RegisterUser` creates a 16-byte protocol salt `S`, stores it in a caller
  supplied map, and returns an encrypted registration record. Password
  Manager does not currently invoke it for website credentials.
- `AuthenticateUser` implements Protocol 2 using the local salt and
  registration record, but Password Manager does not invoke it before reveal.
- `DeriveKey` already uses Argon2id with 64 MiB memory, 3 iterations,
  parallelism 4, and a 32-byte key. Keep these parameters unchanged.
- The vault file stores its version, KDF parameters, master KDF salt, and
  plaintext website index outside the AES-GCM ciphertext. These fields are
  currently not authenticated as AES-GCM additional authenticated data (AAD).

## Approved design

### Per-website protocol identity and salt

- Treat each `(website URL, username)` pair as a distinct demo identity so the
  same username on different websites cannot collide in the in-process maps.
  Construct the identity with an unambiguous, length-prefixed encoding of the
  normalized website URL and username. Keep the original website and username
  as the displayed and stored credential fields.
- Use the protocol salt `S` generated by Protocol 1 as the per-website salt.
  Do not generate a second unrelated salt. Add a `RegisterUser` API path that
  accepts a caller-provided 16-byte salt while retaining existing overloads;
  this lets Password Manager persist `S` inside the encrypted `VaultEntry` and
  use the same value for subsequent Protocol 2 checks.
- Keep `VaultEntry::salt` as the encrypted per-entry storage location. The
  master vault salt remains separate and is used only by Argon2id.

### Add credential: Protocol 1

- After validating the website URL and required fields, create the per-website
  identity and a fresh 16-byte protocol salt using the existing CSPRNG-backed
  salt generator.
- Invoke Protocol 1 (`RegisterUser`) with the website identity, the
  user-entered password, the supplied salt, and an in-process demo server
  record store. Since `RegisterUser` wipes its password argument, pass it a
  temporary password copy and retain the original bytes only for vault
  encryption. Preserve the returned registration record in that store for the
  current app run.
- Store the original normalized website, username, user-entered password, and
  protocol salt in the encrypted vault entry. Commit the vault update
  atomically. If registration, encryption, or persistence fails, do not report
  success or leave a partial credential record.
- If the process-local server record store is unavailable after app restart,
  rebuild it after the vault is successfully unlocked: register every
  decrypted entry with its existing encrypted per-entry salt and password.
  Pass a temporary copy of each password because Protocol 1 wipes its input.
  Do not change the persisted credential data merely to rebuild demo state.

### View credential: Protocol 2

- The existing master-password reveal gate remains in effect. Before displaying
  or copying a selected entry's username or password, authenticate that
  website identity with Protocol 2 using the entry's stored protocol salt,
  its user-entered password, and the corresponding in-process registration
  record.
- Keep the existing ten-minute reveal session. Protocol 2 is required for a
  credential the first time it is revealed in a session; after successful
  verification, the session may reveal other entries without another master
  password prompt, but each entry must still pass Protocol 2 before its
  username/password is exposed. The per-entry protocol check is fast and
  preserves the paper's authentication step.
- Missing records, identity mismatches, empty/wrong-length salts, or failed
  Protocol 2 checks fail closed: keep the selected credential hidden and show
  an actionable failure status. Do not silently bypass authentication.
- Because this prototype has no real website server, the local demo store
  stands in for Protocol 1/2 server records only during the current process.
  Unlock reconstructs records from vault entries as described above.

### Authenticated vault header and version migration

- Keep the plaintext website index to support locked browsing. Bind it and all
  security-relevant file metadata to the encrypted payload with AES-256-GCM
  AAD: file format version, Argon2id parameters, master KDF salt, website
  index count and ordered URL values, and the GCM nonce. The nonce may be
  included in AAD when using the existing `IV || tag || ciphertext` blob
  format; the implementation must use exactly the nonce that initializes GCM.
- Define one canonical, deterministic byte encoding for AAD, independent of
  QDataStream implementation details. The file parser must reconstruct the
  same bytes from decoded metadata. Any mutation to a supported header field
  or website index must cause GCM authentication to fail before entries are
  returned.
- Bump the vault file format version. New files use the authenticated format.
  Continue reading v1 files for migration: after the user unlocks a v1 file
  successfully, preserve its entries, assign a fresh 16-byte Protocol 1 salt
  to each legacy entry that lacks one, encrypt and save it as the new format
  using atomic replacement, and rebuild the in-process Protocol 1 records.
  Never rewrite a v1 file before successful decryption. A failed migration
  leaves the original file intact.
- Wrong master passwords, invalid AAD, unsupported/corrupt metadata, and
  migration-write failures fail closed without returning partial entries.

## Compatibility and data handling

- Existing callers of `RegisterUser` remain source-compatible; the explicit
  salt overload is additive and validates that the provided salt is exactly
  16 bytes.
- New per-website salts are encrypted within the vault entry. The plaintext
  website URL index remains the only credential-related plaintext metadata.
- Existing Argon2id settings and AES-256-GCM remain unchanged. This design
  adds authenticated metadata and does not claim to alter or strengthen the
  underlying Auth protocol.
- Existing v1 vaults migrate only after a successful unlock. Since current v1
  entries may contain an empty salt, migration creates and persists a fresh
  protocol salt before Protocol 1 registration.

## Failure behavior

- Salt generation, Protocol 1 registration, vault serialization, GCM
  encryption, and atomic file-save failures must leave the prior saved vault
  unchanged and must not show success.
- Protocol 2 failures never expose or copy the selected username/password.
- Authenticated-header failures never return any decrypted entries.
- Unsupported versions remain rejected; malformed v1/v2 lengths and indexes
  remain rejected by the file parser.
- QR Sync source and behavior remain untouched.

## Acceptance criteria

1. Every newly added website credential has a random 16-byte protocol salt
   distinct from the master vault salt, and the salt survives app restart
   encrypted in the vault.
2. Adding a website credential invokes Protocol 1 and creates an in-process
   server record scoped to its website-and-username identity.
3. Identical usernames on different websites do not collide; duplicate
   website-and-username identities follow an explicit rejection path and do
   not overwrite the prior record or credential.
4. Every entry reveal/copy passes Protocol 2 for the matching identity and
   record; missing, mismatched, or invalid data leaves secrets hidden.
5. After a successful vault unlock, current-run Protocol 1/2 demo records can
   be rebuilt for all saved entries from their stored salt and password.
6. The vault GCM authentication covers version, KDF parameters, master salt,
   website index, and nonce. Changing any of these makes decryption fail.
7. A v1 vault with a correct master password migrates atomically to the new
   format and gains per-entry salts; wrong passwords or failed writes preserve
   the original v1 file.
8. Argon2id remains configured at 64 MiB, 3 iterations, parallelism 4, and
   32-byte output. QR Sync and password-generation behavior are unchanged.

## Out of scope

- A remote website server, persistent server-record database, or real
  third-party website login.
- Changing Protocol 1/2 cryptographic algorithms or the app's general Auth
  account behavior.
- Password generation, QR Sync, account synchronization, or unrelated UI
  redesign.
